과제 7 · 플랜두씨 다이어리 2

GET /rest/v1/<자료 테이블>
Authorization: Bearer <로그아웃 전에 받은 토큰>
→ 200 OK
→ 내 자료가 그대로 조회됨

200 뚫렸습니다

JWT는 상태가 없어서, signOut()은 리프레시 토큰만 무효화합니다. 로그아웃한 뒤에도 토큰은 한동안 살아 있었습니다.

→ 200 OK
→ 0건

0건 막혔습니다

모든 RLS 정책에 session_is_active()를 추가했습니다. 같은 요청이 200이면서 내 자료 0건으로 바뀌었습니다.

과제 8 · 패스키 소개 페이지

패스키 삭제 요청을 재확인 왕복 중에 연타
→ 401
→ 남은 패스키 0개 (계정 소멸)

0개 뚫렸습니다

재확인 왕복 동안 화면이 살아 있어서 삭제 요청이 겹쳤고, 마지막 패스키까지 지워졌습니다.

→ 200
→ 남은 패스키 1개 유지

1개 막혔습니다

삭제하는 동안 목록을 잠그고, 연타를 재현하는 검사를 추가했습니다.

과제 8 · 패스키 소개 페이지

POST 계정 생성 challenge (로그아웃 상태) × 반복
→ 요청마다 새 계정 생성
→ 제한 없음

무한 뚫렸습니다

로그인하지 않았으면 무조건 새 계정을 만드는 구조였습니다.

→ 11번째 요청부터
→ 429 Too Many Requests

429 막혔습니다

IP 기준 속도 제한을 걸어, challenge를 발급하기 전에 먼저 막습니다.

방어전 · 공개 노출된 자료실

GET /api/notes
(로그인 없음)
→ 200 OK
→ 모든 메모가 목록에 보임

200 뚫렸습니다

시작 상태의 자료실은 비로그인으로도 전부 보였습니다.

→ 401
→ 단계별 점검 500/500

401 막혔습니다

로그인, 소유자 검사, 서버 단일 경로까지 5단계로 막았습니다. 공개 키로 직접 조회해도 401입니다.

요청을 보내면 응답이 여기에 나옵니다.

게임과 제작 도구, 정보판을 만들다 인증(Supabase Auth·RLS)과 패스키(WebAuthn)로 넘어왔고, 패스키 보안을 직접 측정한 논문까지 썼습니다. 이어진 방어전 실습에서는 공개 노출된 자료실을 5단계로 지켜 500/500점을 받았습니다. 4인 팀 프로젝트 NEXUS WORK에서는 조장으로서 자동화와 공격 시험을 맡았습니다.

보안 결함을 반복해서 겪어도 원인을 끝까지 추적하고, 흔들려도 하루 안에 제자리로 돌아옵니다. 동료들에게는 “대화를 나누면 어느새 여러 사람이 웃고 있다”는 말을 들었습니다.

기록

문제 정의, 원인, 조치, 결과 순서로 남긴 보안 트러블슈팅입니다. 각 항목을 열어 보세요.

과제 7 · 인증과 격리
  • 로그아웃 후에도 같은 토큰으로 자료 조회원인 JWT는 stateless · 조치 모든 RLS에 session_is_active() 추가
    200+내 자료 → 200+0건
  • 격리 검사가 스키마 오류(400)를 거절로 오인원인 없는 칼럼을 수정 대상으로 지정 · 조치 실제 칼럼과 반영 행 수·전후 건수로 판정
    양방향 0행 입증
  • 비밀값 탐지 룰 오탐원인 라이브러리의 sb_secret_ 접두어 리터럴 · 조치 실제 키 형태 정규식으로 정밀화
    오탐 0건
과제 8 · 패스키
  • 패스키 하나 삭제 중 계정 소멸원인 재확인 왕복 중 삭제 요청 경합 · 조치 삭제 중 목록 잠금 + 연타 재현 검사
    401·0개 → 200·1개
  • 로그아웃 상태에서 계정 무한 생성원인 비로그인이면 무조건 새 계정 · 조치 IP 기준 속도 제한, challenge 발급 전 429
    11번째부터 429
  • 배포 후 공개 주소에서만 검사 실패원인 운영 DB 마이그레이션 누락 · 조치 재실행해도 안전한 if not exists로 스키마 적용
    41/42 → 42/42
